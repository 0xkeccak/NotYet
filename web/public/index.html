In plain English

Like an advent calendar — for money.

An advent calendar has little doors, one per day. You can't open tomorrow's door today — the date simply hasn't arrived. Notyet does that with an AI assistant's spending money.

Step 1

You set it once

Hand your assistant a sealed budget for each day — say $20 a day for a month — and walk away. You don't keep a copy of any key.

Step 2

It spends on schedule

Each day's envelope opens by itself, on time, unlocked by a public clock that ticks for everyone. The assistant pays for what it needs — no passwords, no company holding your keys.

Step 3

Nothing can be rushed

If the assistant is tricked or hacked, it can only ever touch today's envelope — never the whole month. Tomorrow's simply doesn't exist yet.

That's the whole idea. Everything below is how we make that true with cryptography instead of trust.

The problem

Every agent scheduler is a server holding every future key.

Autonomous agents need authority on a schedule — daily budgets, per-shift credentials, windowed signing. Today there are two ways to give it, both broken:

Approach A

Hand it everything up front

A compromised or prompt-injected agent burns the whole month in an hour. One bad instruction, total loss.

Approach B

A server releases keys just-in-time

Cron, a secrets manager — something holds every future key. It's the honeypot, the single point of failure, and the coercion target.

Session keys solve expiry — authority can end. Nothing solves start. Authority always exists the moment it's issued. So we deleted the server.

How it works

Encrypt each key to a moment in time.

Each period's spend key is timelock-encrypted (tlock) to a future round of the drand beacon — a threshold network publishing a signature every 3 seconds. That signature is the decryption key, and it does not exist until the round happens. The owner pre-issues the whole schedule, hands the agent every locked key, and walks away.

🔒
drand / tlock

The lock itself

Keys are born on schedule. Decrypt early and it throws NOT_YET — for anyone, including the owner.

🔑
Ledger

Root of authority

The issuer key lives on the device and signs the schedule with one on-device confirmation. The agent never holds it.

🌐
ENS

Root of trust

The signed schedule + issuer address live on an ENS name. The agent reads its rules there and refuses if the signature doesn't verify.

⚡
Hedera

Money + audit log

One funded account per period (a ledger-enforced cap), x402 payments via Blocky402, and an HCS log of ciphertexts + encrypted receipts.

Two chains, no bridge: ENS on Sepolia names the agent and holds its rules; Hedera holds the money. The ENS record just points across.

Why it matters
